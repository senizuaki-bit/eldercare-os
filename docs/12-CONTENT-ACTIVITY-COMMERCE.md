# 12 — 内容、活动、推荐与增值服务

本模块负责“老人生活丰富度”和“可持续商业化”，但优先级永远低于安全、基础照护和老人自主选择。

## 1. 产品边界

平台可以提供：

- 机构公告、天气、新闻和生活资讯
- 戏曲、音乐、故事、益智内容
- 兴趣画像、活动推荐、报名、签到、反馈
- 机构自营或审核服务商提供的生活/康复/陪伴服务
- 服务包、订阅、家属代付、履约和评价
- 明确标识的推荐流

平台不得：

- 用孤独、疾病恐惧、情绪低落制造转化压力
- 将广告伪装为照护建议或紧急提醒
- 未经审核销售高风险医疗、金融、保健品或长期合同
- 因佣金而降低免费/更适合选项的排序
- 在老人拒绝后持续重复推送

## 2. 内容中心

### 内容类型

- NEWS：新闻摘要
- WEATHER：天气与穿衣提醒
- FACILITY_NOTICE：机构公告
- SAFETY_ALERT：公共安全/防诈骗
- EDUCATION：健康与生活科普
- ENTERTAINMENT：戏曲、音乐、故事
- FAMILY_MEDIA：家属授权分享的照片/语音/视频元数据
- SPONSORED：明确标识的赞助内容

### 内容状态机

```text
DRAFT -> IN_REVIEW -> APPROVED -> SCHEDULED -> PUBLISHED -> ARCHIVED
                 \-> REJECTED
```

新闻/公共安全内容必须保存：来源、原始标题、发布时间、抓取时间、摘要生成版本、审核人和地区适用性。

### 播报流程

1. 检查老人内容同意、语言、听力、认知适配、免打扰时间。
2. 根据偏好选择内容，不使用健康/情绪敏感信息做商业定向。
3. 内容智能体生成短版播报稿；事实字段必须来自内容记录。
4. TTS 生成语音或使用文本大字显示。
5. 老人可暂停、跳过、追问、减少此类内容、举报不准确。
6. 保存最小播放记录和偏好反馈。

## 3. 兴趣画像

`InterestProfile` 应支持：

- 主题：象棋、书法、戏曲、园艺、历史、散步等
- 偏好强度：主动选择/一般/不感兴趣
- 参与方式：个人、小组、室内、户外
- 时间偏好
- 辅助要求：轮椅、听力设备、陪同
- 明确禁忌或不适合条件
- 来源：老人本人、家属、工作人员观察
- 最近确认时间

任何工作人员推测都必须和老人主动选择分开保存。

## 4. 活动管理

### 数据模型

- ActivityTemplate
- ActivitySession
- ActivityEligibilityRule
- ActivityRecommendation
- ActivityEnrollment
- ActivityAttendance
- ActivityFeedback
- ActivityEscortTask

### 活动状态

```text
DRAFT -> PUBLISHED -> OPEN_FOR_ENROLLMENT -> FULL/CLOSED
      -> IN_PROGRESS -> COMPLETED -> REVIEWED
      -> CANCELLED
```

### 报名状态

```text
RECOMMENDED -> INVITED -> ENROLLED -> CONFIRMED -> ATTENDED
                     \-> DECLINED
                     \-> WAITLISTED
                     \-> CANCELLED
                     \-> NO_SHOW
```

### 可解释推荐

推荐记录至少包含：

- 推荐老人、活动场次
- 推荐原因数组
- 是否满足活动能力/时间/地点条件
- 是否需要陪同
- 是否收费
- 算法/规则版本
- 老人反馈

示例原因：

```json
{
  "reasons": [
    "老人主动选择象棋兴趣",
    "过去两次象棋活动均参加",
    "活动时间与护理计划无冲突"
  ]
}
```

## 5. 服务目录与服务包

### 服务类别

- DAILY_LIVING：助浴、理发、洗衣、保洁
- ESCORT：陪诊、陪同、接送
- REHABILITATION：机构审核的康复活动
- COMPANIONSHIP：陪伴、散步、兴趣陪练
- FAMILY_SUPPORT：探视、家庭直播、月报
- DEVICE_SERVICE：设备租赁/维护
- CONTENT_MEMBERSHIP：内容或课程订阅

涉及医疗行为的服务必须由合法主体、合格人员和单独流程提供；平台只做预约、记录和协调，不用 AI 代替资质判断。

### 核心实体

- ServiceProvider
- ServiceOffering
- ServiceVariant
- ServicePackage
- PackageEntitlement
- Subscription
- Recommendation
- Cart/CheckoutIntent（可选）
- Order
- OrderItem
- PaymentAttempt
- FulfillmentTask
- RefundRequest
- SettlementRecord

### 服务包示例

- 基础关怀包：AI 日程提醒、每周摘要、基础活动
- 家属安心包：重要事件通知、月度报告、探视预约
- 生活服务包：每月助浴/理发/保洁额度
- 兴趣活动包：课程与活动次数
- 康复支持包：经审核的康复课程和记录

## 6. 推荐流

### 推荐来源

- 老人主动搜索或询问
- 未完成的明确需求
- 已订阅权益可使用
- 活动/服务到期提醒
- 工作人员明确配置
- 低风险规则匹配

### 禁止作为直接商业触发器

- 单次负面情绪
- 紧急事件
- 未经复核的健康异常
- 家庭矛盾
- 认知脆弱推测
- 护工为了绩效主动推销

### 排序原则

1. 安全与基础照护
2. 免费/已包含权益
3. 老人主动偏好
4. 适用性和服务质量
5. 价格与可取消性
6. 商业因素只能作为末级且必须可审计

每个推荐必须可回答“为什么推荐给我”和“如何关闭此类推荐”。

## 7. 下单、支付与代付

### 订单状态机

```text
DRAFT -> PENDING_CONFIRMATION -> PENDING_PAYMENT -> PAID
     -> FULFILLMENT_SCHEDULED -> IN_FULFILLMENT -> FULFILLED
     -> COMPLETED
     -> CANCELLED
     -> REFUND_REQUESTED -> PARTIALLY_REFUNDED/FULLY_REFUNDED
```

### 首版支付

使用 `FakePaymentProvider`：

- 支持成功、失败、取消、超时、退款 fixture
- 使用幂等键
- 不保存真实银行卡/支付凭证
- Webhook 模拟必须验签接口和重放保护

真实支付属于独立里程碑和安全评审范围。

### 二次确认规则

下列情况要求家属/工作人员共同确认：

- 高于机构配置阈值
- 长期订阅或自动续费
- 老人存在经人工确认的认知支持需求
- 高风险服务
- 家属代付但服务对象为老人

老人必须知道服务内容、价格、执行者、取消和退款方式。

## 8. 履约闭环

1. 订单支付/确认成功。
2. 生成 `FulfillmentTask`，必要时映射为护理 `WorkOrder`。
3. 指派机构人员或审核服务商。
4. 服务前提醒老人和家属（按偏好）。
5. 服务人员签到、开始、结束；只获得完成服务所需的数据。
6. 上传结构化完成记录和必要附件。
7. 老人/家属确认或进入争议窗口。
8. 完成评价、结算或退款。
9. 结果进入老人时间线、服务质量和财务报表。

## 9. 供应商门户边界

服务商只可访问：

- 分配给本服务商的订单
- 完成服务所需的老人称呼、地址/房间、时间和必要注意事项
- 自己的履约、结算和评价

不可访问：完整健康档案、家庭沟通、情绪观察、其他订单、护工位置、机构全量报表。

首版可先只实现机构内部服务运营角色，不实现独立供应商前端，但数据模型和权限不得阻断后续扩展。

## 10. 退款、争议和投诉

- 退款申请必须保存原因、证据和处理人。
- 履约争议不能由同一服务人员单独裁决。
- 老人可通过语音发起投诉，AI 仅分类和摘要。
- 投诉不会自动公开或直接扣罚员工。
- 严重投诉关联质检/事件复盘。

## 11. 报表

- 内容发布量、播放完成率、偏好反馈
- 活动推荐、报名、满班、到场、取消、满意度
- 服务推荐曝光/接受/拒绝（不得单独优化老人脆弱性转化）
- 订单、客单、退款、履约时长、服务质量
- 服务包订阅、权益使用和续费
- 免费权益和付费服务的覆盖公平性

## 12. 必测失败场景

- 内容来源缺失：不得发布新闻。
- 已撤回内容同意：停止后续播报。
- 活动满员：进入候补，不能超卖。
- 活动取消：通知并处理已付费用。
- 重复支付 webhook：订单只结算一次。
- 订单履约超时：升级服务运营。
- 老人拒绝推荐：同类频控生效。
- 情绪观察为高风险：商业推荐暂停。
- 家属无代付权限：拒绝并审计。
- 服务商跨订单读取：拒绝并审计。
